Eight open problemsoff-list is fine

You pick the direction. These are the problems we think are most neglected relative to how much they matter.

Training compute is the one input to frontier AI you can physically count. Nobody has built the accounting for it.

Policy proposals lean on compute thresholds as the trigger for almost everything: reporting duties, licensing, export controls. The thresholds are written. The mechanisms that would make them mean anything are not.

Who holds which chips, how much of a cluster a given run actually consumed, what counts as one training run when it is spread across three data centres and six months — these are measurement and attestation questions, and right now they are answered on trust.

Where to start

  • A credible chip-inventory scheme that a regulator could audit
  • Metering that survives an operator who wants to under-report
  • What a threshold means once training is distributed

When an API returns an answer, you have no way to check which model produced it.

A provider can silently route you to a smaller model, a quantised one, or the same weights behind a different system prompt. You would not notice, and no deployed system gives you the means to find out.

That matters well beyond consumer trust. Every safety commitment of the form "we run evaluations on the deployed model" quietly assumes the deployed model is the one you evaluated.

Where to start

  • Cryptographic proofs of which weights served a request
  • Statistical fingerprinting that holds under adversarial serving
  • What a verifiable-inference guarantee should even claim

There is no code signature for weights.

Given a model file, you cannot establish who trained it, on what data, under which safety process, or whether it has been modified since it left the lab. The provenance chain that we take for granted in software supply chains simply does not exist here.

Every downstream control — registries, licensing, incident response, open-weight release policy — assumes an identity for the artefact that nothing in the pipeline actually provides.

Where to start

  • Signing and provenance formats for weights and checkpoints
  • Detecting post-release tampering and fine-tune drift
  • Binding a training process to the artefact it produced

Every software guarantee eventually bottoms out in an accelerator you did not build.

Confidential computing on GPUs is where compute governance, weight security and inference verification all have to land. The attack surface is barely mapped: firmware, side channels, physical extraction, and the trust you implicitly place in one vendor's attestation roots.

This is the corner of the field where classic hardware security experience transfers almost unchanged, and where there are strikingly few people looking.

Where to start

  • Breaking or hardening GPU confidential-computing modes
  • Side-channel and physical-extraction work on accelerators
  • What happens when the attestation root itself is the adversary

A frontier model is a few terabytes that a state intelligence service would like to walk out with.

Defending them is an insider-threat and exfiltration problem at a scale most security teams have never had to run: thousands of people with legitimate access, research velocity as an explicit competing goal, and adversaries at the top of the capability ladder.

The published threat models are good. The engineering that would actually satisfy them — egress control that researchers tolerate, compartmentalisation that survives a reorg — is mostly unwritten.

Where to start

  • Exfiltration paths that survive a cooperative insider
  • Access control that does not collapse under research velocity
  • Making a published security level actually verifiable

Any international agreement on AI needs parties to check compliance without opening their labs to each other.

That is a technical question before it is a diplomatic one. Remote attestation, hardware-enforced limits, privacy-preserving audit — the agreement can only promise what some mechanism can check.

Arms control is the obvious precedent and it does not port over cleanly: no radiation signature, no missile silo visible from orbit, and the thing being limited is a computation.

Where to start

  • Verification schemes that reveal compliance and nothing else
  • Hardware-enforced limits a counterparty would accept
  • Which commitments are checkable at all, and which are theatre

Agents read untrusted text and then act with real credentials.

Prompt injection is the case everyone names, and it is the easy one. The harder problems are delegation, revocation, and containment once an agent is several steps into a plan it formed itself.

Most deployments today run on conventions rather than boundaries: the agent is trusted because it is ours, the tool is safe because we wrote it. That does not survive contact with an adversary, and the number of agents with production access is going up fast.

Where to start

  • Real trust boundaries between an agent and its tools
  • Delegation and revocation for credentials an agent holds
  • Containment and audit after an agent goes off-plan

Deciding what a given user may get out of a model is an access-control problem wearing a safety costume.

Refusal training is a blunt instrument applied at the wrong layer: it treats every request as anonymous and every user as identical, then tries to guess intent from the text alone.

What is missing is the ordinary machinery of authorization — graded permissions, identity that survives the API boundary, audit that holds up after the fact — applied to capabilities rather than endpoints.

Where to start

  • Graded capability authorization instead of blanket refusal
  • Identity and accountability that survive resale and proxying
  • Audit trails that answer who asked for what, afterwards
